10 days from the first commit to v1.0.0

The port's first commit is dated 16 October 2026; v1.0.0 was tagged on the 25th. In between, the work followed a plan written down before any code: what to find out, what to build, in which order, and how each part would be checked on a real Atari ST.

This page is about that plan: the method, the path it took, and the places where it changed its mind.

Four sizes of work

The plan has four levels, each a different size of promise:

Iteration
one goal that takes several epics, with a sentence saying when it is over. "Level 1's world" ends when level 1 scrolls end to end at a steady 50 frames a second on a plain ST and an STE.
Epic
a capability, such as the ship, the sound or the shop. Epics run one at a time, in order, and each ends at a checkpoint on real hardware.
Story
a slice of an epic that can be shown working: the map decoded, the scroll model, the effects driver.
Task
a checkbox inside a story. A task is ticked only when someone has seen it done, never because it was built.

The numbers on the plan are its order of execution, and a short script turns the checkboxes into a status page, epic by epic, so where the work stands is always one command away.

Reverse, then build

The game's code had to be understood before it could be rewritten, so the first epics come in pairs. An analysis epic finds out what the original does: how it boots and loads, its real frame rate, its level formats, how the ship moves, how the sound driver works, how enemies follow their paths. Its findings go into notes that are reproduced on the original before anything is built on them. The build epic after it writes the C, checked against those notes and against the original running in Hatari.

The first analysis set the whole project's terms. Measured in Hatari, the original shows 16.58 frames a second over 384 frames of level 1: a frame every three vertical blanks, and now and then a fourth. From then on, "50 frames a second" meant three pictures for every one of the original's.

Later epics, once the method was routine, carry their analysis as their first story instead of an epic of its own: the bosses, the weapons, the shop, each level from the second on.

Nothing merges unseen

Every epic ends with a verification story, and that story belongs to the author: the epic is built, flashed onto a Multi-device and played on a real Atari ST before its work is merged. An analysis epic's checkpoint is its findings reproduced on the Mac.

  1. A release branch is cut from the main branch, named after the version it will become.
  2. Each epic gets its own branch, cut from the release branch.
  3. The epic's pull request goes to the release branch, never to the main branch, and is merged only after its checkpoint on hardware.
  4. When the whole version is done, the release branch is merged into the main branch, once, and only then tagged. The tag builds the release and publishes it.

Every pull request also builds both firmware variants and runs the host tests, so the checkpoint on hardware judges the game, not whether it compiles. Timings that feed a decision are taken on a release build, never a debug one.

Decisions, written down

Anything that cuts across epics is a numbered entry in a decisions log, with its date, who decided, the reason and its status: where the converted game lives, how sound reaches the ST, which machines count, what "50 frames a second" means for the game's speed. Stories cite an entry instead of arguing the point again. Beside the decisions sit the constraints (nothing from the game is ever committed; per-frame work never touches the card; the cartridge code stays under 16 KB) and the facts about the original, each with its source.

A decision that turns out wrong is not deleted. It is marked superseded and points at the one that replaced it, so the log shows how the project's thinking moved, which is what the next section is made from.

The path

Eight iterations, in the order they ran. Each had its goal fixed before it started.

  1. Workbench and first light

    16 October

    A scripted Hatari harness of the project's own; the loader, the disks' layout, the memory map, the main loop and the real frame rate. Then the app on the framework: the user's disks converted on the cartridge, and the title screen on an ST.

  2. Level 1's world

    17 October

    The performance proof, first because nothing else would matter without it. The level formats decoded until a renderer on the computer matched the original pixel for pixel; then the playfield drawn on the RP2040 and scrolling at 50 frames a second.

  3. The ship and the sound

    17 October

    The Megablaster decoded and flying, dying and coming back; the sound driver understood, played back on the computer, then on the ST's own sound chip.

  4. Enemies and bosses

    17 October

    The waves and paths decoded, the enemies in play, level 1's end boss and the way to the next level: level 1 playable from start to finish.

  5. The rest of the game

    17 and 18 October

    Every weapon and token and the dive; then Crispin's shop, the attract screens, two players, continues and the high scores.

  6. Levels 2 to 5

    18 to 25 October

    Each level's own code moved behind a table of hooks, level 1 first, then each level ported and checked against Hatari: its scenery, its mid boss, its end boss, and the ending after the fifth.

  7. Smooth paces

    25 October

    How the game moves at 50 frames a second: the world a line every vertical blank, the sprites at the original's speed drawn in between, or three times as fast.

  8. Options and the release

    25 October

    The options screen, the levels converted once at the first start, the documents, and the tag.

Where the plan changed

A plan written before the work is a guess. These are the places where the work proved it wrong, as the decisions log records them.

The game's speed, four times

The first plan ran the game's logic at 50 Hz with every movement scaled down to keep the original's speed. Then, during level 1, a debug key ran one original frame every vertical blank, everything three times as fast, and it was a different game, and a good one: it became an option. Next, after level 1's enemies, the plan became "the original's speed for everything, only smoother". The model that shipped came last, on an STE: the frame rate drives the scroll, and the sprites either keep the original's pace, drawn between their steps, or run at ×3. Four entries in the log, each superseding the one before.

No interpreter, after all

On the second day the sound driver, and then the shop, ran the original's own 68000 code in an interpreter on the RP2040: quick to get right, since it was the original. A day later that was reversed for good: no 68000 interpreter in the firmware, for anything. The driver and the shop were rewritten in C like everything else, and checked write for write and pixel for pixel. An interpreter may still serve on the computer, as a reference while porting.

Flash, measured

Where a level should live while it plays was left open until it could be measured. A converted level came to 150 to 262 KB against about 56 KB of free RAM, so the levels went to flash, read in place, with the RAM keeping only the map that the level's code rewrites.

Four levels in one run

Levels 2 to 5 were planned as two epics with a checkpoint each. Once level 2's plan was approved, the remaining levels were ported in one run, each still checked against Hatari, and the smooth paces, planned for level 1 only, grew to cover all five levels since they were already built.

Why the notes stay private

The plan lives on the developer's machine, outside the repository, and nothing committed names one of its items: no code comment, commit message or pull request says "as planned in such and such". A reader of the code cannot open the plan, so a pointer to it tells them nothing; the code and its comments say what they do and why, in full. The only place the plan shows is the name of each epic's branch. That is also why this page tells the path by what was done, not by the plan's numbers.

The same layout, the same fields and the same status script are used across SidecarTridge's projects, so each one's work is tracked the same way.
